AFTERMATH Blueprint

A Docker-only intrusion range that arrives already compromised: one installer brings up the SIEM, the edge, two network sensors, a weak Linux workstation and an attacker, seeds a scenario, backdates it so the timeline matches the ticket, and drops you on a triage dashboard with detection-rule alerts already firing. An opt-in Vagrant tier adds a host-based DFIR victim — a standalone Windows 10 box running Sysmon and Atomic Red Team. A domain (AD) tier is on the roadmap, not yet built.

The AD tier — roadmap

planned · not built yet · ~6 GB of guests

This tier does not exist yet — it is the intended next step, sketched here so the shape is clear. The Docker default teaches network-side hunting; the standalone Windows 10 box adds host DFIR. An AD tier would add the one thing neither can tell — a domain — so the chain becomes an enterprise story: get onto a workstation, harvest a service ticket, move laterally, persist. It would reuse the same host-only path and the same Atomic-on-the-victim model as the standalone box. Building it means two more guests and domain-join automation, which is why it's deliberately held back rather than bolted on.

The network tier — roadmap

planned · the step after AD

Also not built — the intended addition once the AD tier lands. A perimeter firewall would add the one telemetry class the lab is missing: allow/deny connection logs and a segmented network (victims behind the firewall, not all flat on one bridge). The natural fit is pfSense or OPNsense, optionally running the Suricata package as a perimeter IDS.

The catch that keeps it on the roadmap: pfSense is a full FreeBSD OS, so it can only run as a VM (like the Windows/AD tiers), it has no clean automation (config is GUI/console-driven — no cloud-init), and it can't interpose on Docker's networking — Docker owns the lab_net gateway (172.30.0.1), so a firewall VM can't sit in front of the existing containers. It only works as a separate VM segment alongside the Docker lab.

Why the code looks like that

decisions worth keeping

  1. The Fleet service token is stripped of its newlinefleet-server puts the file's raw contents into the Authorization header; a trailing \n makes it an invalid header value and the server never starts.
  2. Suricata's config is mounted read-writeThe image's entrypoint chowns its own config on startup and exits 1 if it can't — a :ro mount kills the sensor before it sees a packet.
  3. The agent runs as elastic-agent container, under setsid nohupinstall wants systemd, which a container has not; enroll then run tries to reload a daemon that isn't up yet. And the restart uses pkill -x — pkill -f would match the enroll script's own command line and kill the script.
  4. One Elasticsearch output, not twoMultiple hosts in an agent output round-robin rather than fail over, so an address only some agents can reach breaks delivery for everyone. The Windows VM maps the in-Docker names to the host in its hosts file instead.
  5. Logstash reads from the start of every filesincedb_path => /dev/null means a restarted lab re-ships the seeded history instead of a Discover view that begins at the last boot.
  6. The victim's weakening happens at build timeweaken.sh runs as a build arg step, not from environment: — runtime env would never have touched the account the image already baked in.
  7. An unimplemented technique exits 2A seeder that reports success while generating nothing is worse than one that fails, because the analyst then hunts for events that were never created.
